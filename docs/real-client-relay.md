# 一次真实 Claude → Codex → Claude 开发接力

2026-10-18，Asia/Taipei。使用本机已登录的 **Claude Code 2.1.296**（运行日志报告 `claude-opus-5-5`）和 **Codex CLI 0.149.0**。这次是真实模型客户端调用 EverOS MCP 后开发、测试、回传，不再只是 Python 脚本启动两个 MCP 进程。

## 开发了什么

为 uu-remote-linux 做一个本地测试交接摘要小工具：输入 JSON 测试记录，输出带平台、证据分类和上线限定的 Markdown。它作为本教程的可运行例子交付，**没有修改或部署 uu-remote-linux 的远控核心**，也没有进行真机远控验收。

- [Claude 的阶段 A：解析器与 10 项测试](../examples/uu-handoff/stage-a/)
- [Codex 接手后的成品：解析、渲染、CLI 与 17 项测试](../examples/uu-handoff/finished/)
- [脱敏工具调用与结果摘录](evidence/real-client-relay.json)
- [独立验收检查](evidence/independent_acceptance.py)

## 如何避免把聊天偷偷传过去

1. Claude 使用独立工作目录，先实现 `load_records` 和解析测试。首轮没有 `build_brief`、CLI，也没有交接文档。
2. 将**仅有的两个 `.py` 文件**复制给另一个工作目录。转移文件的 SHA-256 记录在证据 JSON 中；没有复制 `.git`、聊天日志、提示词或说明文件。
3. 新 Codex 会话使用 `--ephemeral --ignore-user-config` 和显式传入的 MCP 配置；只获得任务名与“先检索再继续”的要求，没有 Claude 的完整聊天。
4. 精确标签、输出首尾行与验证口令没有出现在接收方提示词、初始源代码或测试中。它们在运行时通过 EverOS MCP 返回。
5. 接收方被要求只读写自己的工作目录、不读取父目录和会话历史、不用 shell 直连记忆 API。导出的命令记录显示实际做的是当前目录源码读取、修改与本地测试。

这不是密码学隔离：两套 CLI 在同一台机器上运行。我们通过独立新会话、目录、源文件清单、提示词和实际工具事件核对数据路径，没有宣称做了沙箱安全审计。

## 先失败，再修正

### 1. CLI 模型别名被拒绝

本机配置里的 `gpt-6.1-sol` 被该 CLI 的 ChatGPT 账户拒绝，尚未进入开发。之后改用 CLI 自带默认模型，正式运行没有 `-m` 覆盖。这不构成任何型号支持承诺；不同账户请用自己可用的模型。

### 2. “已提取”不等于另一边读到了

首轮 Claude 只提交 `assistant_message`，虽然工具回执是 `Stored and extracted`，Codex 实际搜索与列表仍为空。后端读取也没有找到预期用户记忆。接收方按要求停止，没有猜实现约定。

随后由真实 Claude 新会话同时保存：

- `user_message`：真实用户本次要求进行开发接力验收的原话。
- `assistant_message`：Agent 检查过的文件、测试结果、后续实现约定；明确这些是隔离验收的技术规格，不是生产项目的额外用户要求。

新记录随后可以检索到。这是本次观察到的差异，不把它推广成所有部署的归因规律。不要为了让记忆出现而伪造用户原话，也不要在写入超时后盲目重复提交。

### 3. 长交接丢了精确格式

新记录虽可见，自动提取却把长消息概括成“有首行要求、有标签规则”，省略了首尾行原文、标签映射与 CLI 退出码。

我们没有假装这些信息已经传过去。Claude 接着将格式、分类、CLI 行为拆成三个短条目，实际再次检索确认字面量被保留。它们仍是提取后的叙述体；其中 stderr 的“有简短错误”还被改写成“只输出简短错误”。**短条目在本轮有效，不等于记忆引擎有无损保证。**

这一步还发现旧失败记录可能比新约定排得更高；`top_k=10` 的结果里才包含全部关键条目。因此接收方需要检查时间、补充条目和实际正文，不能取第一条就当最终状态。

## 最终接力结果

| 阶段 | 实际动作 | 结果 |
|---|---|---|
| Claude 开发 | 写 JSON 解析与校验，运行测试 | 10 项通过 |
| Claude 保存 | 保存原始用户任务与实现约定，拆短后读回 | 格式、标签、退出码、口令可见 |
| 新 Codex 检索 | 实际调用 `search_memory`，先拿到约定再读代码 | 取得 A/B/C 与验证口令 |
| Codex 续开发 | 新增 `build_brief`、CLI、3 项渲染与 4 项 CLI 测试 | 总计 17 项通过 |
| 外部验收 | 用事先未交给 Codex 的检查核对输出与 CLI | 5 项通过 |
| Codex 回存 | `add_memory(wait=true)` 保存实际完成与未验证范围 | 返回已提取 |
| 新 Claude 复核 | 从 EverOS 找到 Codex 完成记录，再读取代码、独立重跑 | 17 项通过 |
| 空项目范围对照 | 新 Codex 使用不同 `project_id` 检索同一任务名 | 无匹配记忆 |

Codex 最终返回了仅经记忆获得的口令“纸灯接力，证据先行。”；口令没有写入程序和测试。接力前后 `load_records` 与 `_validate_record` 的 AST 一致，解析契约未改动。

新 Claude 还指出一处报告错误：Codex 把 MCP 的八位 `BEGIN STORED MEMORY` 包装标记称作“记忆 ID”。**它不是数据库 Episode ID。** 本报告不采用那个错误称呼，原始摘录保留这次误述及复核意见。

## 这次能证明什么

这次在明确要求调用记忆工具、使用同一空间和 user/app/project 范围的条件下，真实 Claude 与 Codex 客户端完成了一个小工具的开发接力，且回传状态能被新 Claude 会话读到。

它不证明任意项目、任意模型和任意长交接都能直接成功，也不证明客户端会在没有提示的情况下自动保存所有内容。更不代表完整聊天同步、生产远控已验收，或 Agent Skill 自动提炼已成功。

实际使用建议：**Git 保存代码、精确规格和测试；EverOS 保存项目背景、决定、限制及来源。先读回核对，再交给下一位 Agent。** 本轮故意把精确文本也藏在记忆里，是为了检测传递边界，不建议生产开发只靠记忆保管这些文本。

## 怎样自己复现

先按 README 配好两端相同的记忆范围。然后准备互相独立的 writer / reader 工作目录：

1. 在 writer 中启动真实 Claude Code，按[初始任务](evidence/claude-prompt.txt)开发解析器。可以用仓库的 stage-a 文件对比结果。
2. 保存时同时提供真实用户任务与 Agent 决定。看[修正保存方式](evidence/claude-repair-prompt.txt)和[拆短约定](evidence/claude-short-prompt.txt)，读回确认内容，而不是照抄回执。
3. 只将 writer 的源代码和解析测试复制到 reader。不要把完整示例目录、这些文档或提示词一起复制。
4. 在 reader 新启动 Codex，使用[接收任务](evidence/codex-prompt.txt)。它需要从 EverOS 检索实现约定，而不是读取 writer 聊天。
5. 运行成品测试和独立检查，再用[新的 Claude 评审任务](evidence/claude-review-prompt.txt)检索完成记录并复核。

这些提示词在本次运行**结束后**公开。若你要做新的盲接力验收，应使用新的项目范围、任务名和口令，避免已有公开内容影响测试。授权各客户端读取、编辑、运行测试和所需 MCP 工具；不要把“权限被拒绝”当成工具已经执行。

## 证据怎么整理的

仓库发布的是实际 CLI JSONL 中 MCP 调用、参数、返回和最终答复的脱敏摘录，以及源文件与原始日志 SHA-256。没有发布 API Key、账号登录信息或完整宿主配置。原始调用的工具包装、先失败后修正、长摘要缺失和回传复核都保留在摘录中。
